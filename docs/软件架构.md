## 2. 目标架构

这个软件我是用来填补Android软件的本地功能不足的，所以功能会很杂，说起来它们应该
写成多个软件，但这些功能几乎都依托本地文件管理，再写一个软件就要复制这部分本地
文件管理逻辑了，这就显得不值得。

所以，作为一个最基本的逻辑，我把文件管理作为基础功能来提供，文件管理提供一个“应
用可见”的目录视图。其他功能要不直接从某个文件或者目录上打开，要不基于当前的目录
视图上提供功能，功能间的接口尽量经过文件或者目录的内容来提供。比如说，看书功能
要写一个笔记，这个笔记写到文件中，而笔记阅读软件就从文件中按约定的格式中获得内
容，而不是调用看书功能的接口来获得内容。这样，看书功能和阅读笔记的功能的接口的
耦合就比较小，不会修改一边就立即破坏另一边，文件格式要实现多版本间兼容要容易很
多，甚至未来我要用另一个程序来读这个笔记，也没有任何问题。

功能我分成两种：

1. TAB功能：这种功能以TAB的形式现实在主界面上，某个时刻只能打开某个TAB，切换到
   另一个TAB的时候，当前TAB会保留部分工作状态，再切换回这个TAB，这个状态通常会
   保留，让用户觉得这个功能还在。这通常用于某个独立的功能，它不依赖其他功能而独
   立存在。文件浏览，音乐播放，git访问……这些功能每个都可以是一个独立的TAB功能。

2. 弹窗功能：这包括文件阅读，文件/目录压缩/解压缩、加密/解密等等，这些功能从某
   个TAB功能的基础上启动，带着那个TAB启动它的一个子参数，完成后会回到TAB功能上。
   比如一个文件浏览的TAB上打开一个pdf文件，显示pdf的功能只收到要显示的pdf的路径
   要求，按要求阅读这个pdf文件，用户关闭这个弹窗后，界面回到文件浏览的TAB上，弹
   窗功能不再保留任何界面状态。当然，这也不影响该功能保留一些全局配置或者在文件
   系统中留下更新的信息。

所有这些设计的目的都是为了解耦，减少模块之间的依赖：

* 主程序只关心有多少TAB，无论TAB怎么绘制，都不用考虑主程序怎么写，它绘制好自己
  的内容就行。主程序的逻辑就是管理输入参数（比如Actity的启动Intent参数等），然
  后根据历史记录，崩溃情况，用户选择等情况，选择一个TAB显示。这样未来增加TAB，
  基本不会影响主程序。

* TAB中的子功能，尽量再分解为弹窗功能，弹窗暂时占据TAB的控制界面，单独完成一个
  功能，完成后就退出，不保留UI意义上的创建，比如做一次压缩，完成压缩后产生压缩
  文件，但下次再压缩，和之前的压缩没有什么关系，就是一次独立的行为。这种功能容
  易共享，比如在“文件浏览”TAB中可以显示pdf文件，“最近”TAB中同样可以显示pdf文件，
  显示pdf文件这个功能本身不假设它自己是被谁弹出的，只要知道要显示哪个pdf文件就
  行。

* TAB功能和弹窗功能之间的接口优先选择文件接口：做完一个功能，改变了文件，再启动
  下一个功能，基于最新的文件状态完成新的功能，这样每个功能的入口都很清楚。当然，
  并非所有的功能都可以这样做，我们同样允许部分功能直接更改当前的状态，比如文件
  浏览中增加一首歌到播放列表中，如果写到文件中，就需要播放器反复读文件更新状态
  了，这种可以调用播放器TAB功能的函数进行动态接口，但这不影响显示，因为当前只有
  文件浏览功能的UI可见，播放器并不可见，具体使用那种方式，具体问题具体分析。

### 2.1 配置共享

应用中有很多配置，现在逻辑是比较乱的，有些是属于功能，有些属于全局，但功能有可
能有共享，然则功能的配置也是全局的。所以我现在一般认为配置分两种：

* 持久配置：可以跨实例持久化的，比如你在一台手机上安装了，导出来，可以导入到另
  一台手机上。
* 本机配置：可以在本地持久化的，比如你设置了某个属性，这个不能导出，但下次启动
  应用，这个内容还在。
* 本次配置：只在运行期间有效的，这种程序退出后，下次再启动程序，配置就恢复到默
  认值了。

这是配置自身的属性，但在哪里配置，使用另一套逻辑：

* 很少改的，就是为了偶尔修改了再也不管的，这些放到配置页上。这种常常是持久配置，
  但不严格要求。这种配置可以导出，但平时保存在本部内存存储中。
* 经常修改的，和某个功能绑定的，这个放在功能的上下文中配置。这种常常是本机配置
  或者本次配置。这种配置不能导出，但本机配置需要保存在本机内部存储中，本次配置
  留在内存对象中即可。

那么配置tab的定位是什么呢？是对配置的显示，还是配置的容器呢？我觉得应该是和其他
tab地位平等的一个数据提供者。

## 3. 当前架构状态分析

程序实现在com.kenny.localmanager中，主Activity按一般习惯，是默认的MainActivity。
绘制先按管理先绘制LocalManagerTheme，用来设定配色等基本设置，然后在这个Theme上
绘制真正的界面，Compose FileBrowserApp()。

也就是说，我们整个程序的根是文件浏览器，因为所有功能都认可当前的路径在哪里，这
些信息是全局的，而文件浏览那个Tab本身，只是这个当前路径的一个展示。
