# 家庭网络文件共享设计

## 1. 目标

我们不再把这个功能设计成“PC 端主动启动临时服务并让手机连接”的形式。我们改成更自然的 FTP-like 模型：

- 手机端作为服务端（server）
- PC 端作为客户端（client）
- 共享目录直接绑定到应用的根目录
- 认证方式直接复用现有 FTP 密码 / admin 密码
- PC 端以命令行操作为主，类似 ftp / sftp 的交互习惯
- 可选地提供一个极简浏览器 Web 入口，用于从电脑浏览器直接上传文件

最终目标不是另造一套协议，而是让手机充当一个临时、局域网内的“共享文件服务器”，在大多数情况下可以替代 FTP 的使用体验。

## 2. 为什么这是更自然的设计

### 2.1 FTP 的默认使用方式就是“服务端在手机，客户端在 PC”

用户真正的心理模型：

- 在手机上打开“共享文件”
- 在电脑上用 `ftp` 或 `curl` / 浏览器访问它
- 直接上传/下载/浏览文件

这和我们项目里现有的“家用文件共享”和“应用根目录”最契合。它不需要任何 mDNS，用户也不需要不停地切换到“启动服务”这个动作。

### 2.2 这样可以直接复用已有能力

我们已经有：

- FTP 密码配置
- 应用根目录
- 家庭网络的通用 HTTPS/TLS/密码认证协议
- PC 客户端工具链（platalea）

所以最自然的实现是：

- 让手机端 create/serve 一个文件共享端点
- 让 PC 端使用 `platalea share-client` 或 `platalea share-cmd` 进行 ls/get/put/rm 等操作

这意味着：

- 现有配置项几乎不需要新增
- 未来若做更高性能的传输层，也能继续在通用家庭网络层内迭代

## 3. 总体架构

### 3.1 角色分工

- 手机端：server
  - 直接绑定应用根目录
  - 使用已有 FTP 密码或 admin 密码
  - 对外提供 FTP-like API
  - 一般在用户主动打开共享时启动，关闭时结束

- PC 端：client
  - 使用命令行 `platalea share-client` 或 `platalea share-cmd ...`
  - 直接访问手机 IP + port
  - 上传下载文件
  - 也可以做 ls / mkdir / rm 等控制命令

### 3.2 原则

1. 手机端 server 是主角色
2. PC 端 client 基于命令行优先
3. 所有网络逻辑都尽量放在通用家庭网络层，而不重复写成独立协议栈
4. Web 入口只作为可选增强，不作为首选体验
5. 服务生命周期短、交互式、手动启动和退出

## 4. 访问方式

### 4.1 命令行：最优先方案

建议新增入口：

```bash
platalea share-client <host> --password <pwd> ls
platalea share-client <host> --password <pwd> get /path/file.txt ./local.txt
platalea share-client <host> --password <pwd> put ./local.txt /path/remote.txt
platalea share-client <host> --password <pwd> rm /path/old.txt
platalea share-client <host> --password <pwd> mkdir /path/newdir
```

或者更 FTP-like：

```bash
platalea share-cmd ls <host> --password <pwd>
platalea share-cmd get <host> /path/file.txt ./local.txt
platalea share-cmd put <host> ./local.txt /path/remote.txt
platalea share-cmd rm <host> /path/old.txt
```

这样最接近 ftp 的使用习惯，也最适合写脚本。

### 4.2 浏览器 Web：可选增强

除了命令行以外，我们也可以支持非常轻量的 Web 页面：

- 在手机端开启“共享目录”时，允许浏览器访问一个本地页面
- 页面上显示当前目录内容
- 支持拖拽上传
- 支持简单下载

注意：这不是首选方案，而是提升体验的可选能力。

## 5. 与现有 FTP 体系的关系

### 5.1 使用现有 FTP 密码

当前应用里已经有 FTP 相关配置：

- ftp password
- ftp port
- ftp timeout
- ftp service configuration

因此最自然的方式是：

- 把“共享目录 server”当成现有 FTP 的局域网扩展
- 复用现有密码和端口配置
- 让手机端直接在同样的 server 端口上提供文件访问功能

这意味着：

- 不需要全新配置项
- 不需要单独存一份“share password”
- 用户理解成本低

### 5.2 兼容性层

如果未来我们需要支持更高性能传输，可以做成：

- 统一连接层：TLS + auth + retransmit
- 文件共享层：ls/get/put/rm
- 兼容层：兼容 FTP 命令与 Web API

这保证后续性能优化不会破坏现有语义。

## 6. 认证与网络设计

### 6.1 认证复用家庭网络协议

推荐继续复用现有家庭网络认证方式：

- TLS/HTTPS
- `X-Network-Service-Password` 头
- 目标用户密码/管理员密码

如果服务端是手机，最好默认采用：

- admin password 作为访问密码
- 或者使用已有 FTP password 作为共享密码

这样就不需要新增一套 token 或 session 概念，接口会更简单。

### 6.2 网络通用层

无论是 share-cmd、浏览器 Web 还是后续的更高性能传输，底层都应该复用通用网络模块：

- 连接建立
- TLS 校验
- 认证头
- 错误处理
- 断线重连
- 消息/流传输

核心目标：

- 文件共享功能先跑通
- 但底层协议可持续优化
- 家庭网络相关收益能够持续反哺到这个功能上

## 7. 服务端实现方案（手机端）

### 7.1 服务端职责

在手机端，需要有一个轻量服务：

- 监听指定 port（默认兼容 FTP 端口或 2121）
- 绑定应用根目录作为共享根
- 处理请求：
  - ls
  - get
  - put
  - rm
  - mkdir
  - stat
- 认证：密码校验
- 生命周期：用户打开后启动，关闭后退出

### 7.2 目录安全边界

服务端必须把共享根锁定在应用根目录之内，不能越界：

- 只允许访问共享根目录
- 禁止 `..` 路径越界
- 禁止访问外部目录
- 所有上传必须落到共享根之内

### 7.3 推荐的接口形式

最实用的接口并不一定是 FTP 协议原生，而是一个轻量 HTTP API，类似：

- `GET /ls?path=/`
- `GET /download?path=/foo.txt`
- `PUT /upload?path=/bar.txt`
- `DELETE /rm?path=/old.txt`

原因：

- 真正的 FTP 协议实现会更重
- HTTP API 更方便浏览器 + CLI 复用
- 未来可以通过通用网络层高性能承载

也就是说：

- 用户看到的是 ftp-like 做法
- 后端实现可以是 HTTP 语义，且复用家庭网络通用层

## 8. PC 端实现方案

### 8.1 命令行 client

建议新增：

```bash
platalea share-client
```

它可支持交互模式：

```text
> connect 192.168.1.10:2121
> ls /
> get /foo/bar.txt ./bar.txt
> put ./notes.txt /docs/notes.txt
> rm /docs/notes.txt
> quit
```

或直接命令式：

```bash
platalea share-cmd ls 192.168.1.10 --password x
platalea share-cmd put 192.168.1.10 ./a.txt /remote/a.txt
platalea share-cmd get 192.168.1.10 /remote/a.txt ./a.txt
```

这样最符合 FTP 的使用习惯，也较容易脚本化。

### 8.2 浏览器 Web 入口（可选）

Web 入口可以作为“低门槛增强”，但不作为第一优先级：

- 从电脑端浏览器直接访问手机端的文件服务页面
- 直接上传文件
- 直接下载文件
- 目录树浏览

优点：

- 电脑端不需要安装额外客户端
- 适合临时、偶发使用

缺点：

- 需要前端 JS 代码和文件上传 UI
- 不是最自然的操作模式
- 增加 APP 体积和维护成本

## 9. 浏览器 Web 接口的价值与成本

### 9.1 价值

浏览器 Web 入口的好处是：

- 直接在电脑浏览器中打开链接即可传文件
- 对于临时文件分享非常方便
- 适合老师/同事/家庭成员快速分享文件

尤其是：

- 不想装额外软件时
- 只需要简单上传下载时
- 电脑端是本地浏览器，自然打开就用

### 9.2 成本：对手机端应用的影响

如果做成“手机应用内嵌一个 web 服务器 + html 页面”，那么主要成本在：

- 提供一个简单前端页面（HTML/CSS/JS）
- 在应用中增加一个本地 WebView 或路由界面
- 处理上传、下载、目录展示
- 需要更复杂的网络层和 UI

对 APK / size 的影响大致可以估算为：

- 一个极简纯静态页面：几百 KB 到 1 MB 左右
- 如果是仅用内置 WebView，不额外引入大型前端库，那么体积增长很小
- 如果做成较完整的文件管理 UI，可能是 1~3 MB

为了更准确地说：

- 纯静态单页文件（HTML/CSS/JS）本身不会很大
- 真正的成本主要在应用代码和 UI 逻辑，而不是单纯的资源文件
- 如果前端只是极简页面，预计增量体积在 0.5~2 MB 左右
- 如果引入更完整的前端框架/复杂库，则会上升到数 MB

这是“可接受范围内的增量”，但它并不是第一优先级。

### 9.3 结论：浏览器 Web 入口是增强功能，不是主功能

因为：

- 命令行方式更自然、更脚本化、成本更低
- 用户主要是大多数时候在电脑侧用命令行/脚本处理文件
- 浏览器模式只是在“临时分享、无需安装客户端”时才有价值

所以推荐：

- 第一期做命令行 client
- 第二期可选做浏览器 Web 页面

## 10. 和家庭网络未来迭代的关系

这是这个方案最重要的一点：

- 这个功能不是独立的“FTP clone”
- 它是在家庭网络之上的一个共享文件应用
- 一旦家庭网络传输层做了性能优化、分块、断点续传、缓存，文件共享功能就能直接受益

比如：

- 更高性能的 HTTP 传输
- 更稳的断线重连
- 目录列表缓存
- 更快的大文件上传
- 更好的并发控制

都可以在通用传输层中实现，而不需要重写 file sharing 业务层。

## 11. 实施顺序

### Phase 1：最小功能闭环

- 手机端共享目录服务
- PC 端 `share-client` / `share-cmd` 命令
- 支持 ls/get/put/rm
- 复用已有 password/port

### Phase 2：稳定性

- 路径越界安全
- 错误处理
- 断点续传
- 目录浏览稳定性

### Phase 3：Web 入口（可选）

- 一个极简浏览器页面
- 仅用于轻量上传下载

### Phase 4：增强

- 批量上传
- 断点续传
- 文件夹同步
- 更高性能的传输策略

## 12. 结论

最终方案应当是：

- 手机端作为服务端
- PC 端作为 client
- 共享根目录绑定应用目录
- 使用现有 FTP / admin 密码
- 以 ftp-like 命令为主
- 使用家庭网络通用协议层做底层传输
- 浏览器 Web 是“增强版”，不是第一优先级

这更符合用户直觉，也最容易和现有代码/配置无缝接合。它同时保留了未来持续优化的可能性：网络性能、认证、传输优化都可以继续在家庭网络通用层不断收益。
