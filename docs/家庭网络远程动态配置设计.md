# 家庭网络 PC 远程动态配置设计（讨论稿）

## 1. 设计目的

### 1.1 背景

当前家庭网络在 PC 端已经具备留言板动态管理能力（建板、删板、板级权限、板级 AI 管理者），但核心控制面仍主要依赖 `config.json` 静态配置。

这与无头工作站（例如 Mac mini 常驻运行）场景不匹配：

1. 管理员希望“首次部署后，后续主要通过手机远程维护”。
2. 当前手机端无法完整管理 PC 角色定义（角色增删改、密码轮换、能力位）。
3. 手机端对板级 AI 管理者的可配置性依赖板内可见模型列表，缺少统一的远程策略入口。

### 1.2 本设计目标

本设计在现有家庭网络协议上新增“远程动态配置平面”，目标是：

1. 支持管理员在手机侧远程维护 PC 的角色和 AI 策略。
2. 明确区分“可热更新配置”和“需重启配置”，避免误操作。
3. 保持与现有留言板协议兼容，优先增量改造。
4. 提供可审计、可回滚、可并发保护的配置修改机制。

### 1.3 设计基线

本设计基于 2026-08-08 代码状态，关键现状来源：

1. [pc_tools/platalea/bulletin_server.py](pc_tools/platalea/bulletin_server.py)
2. [pc_tools/platalea/bulletin_roles.py](pc_tools/platalea/bulletin_roles.py)
3. [pc_tools/config.example.json](pc_tools/config.example.json)

## 2. 现状盘点与问题定义

### 2.1 已具备的动态能力

1. 留言板增删改（名称、`role_ids`、`ai_manager_model`）可通过 `/boards` API 操作。
2. 手机端已可远程打开板并调用板级修改接口。
3. 消息发送链路支持“板级 AI 管理者自动路由 + 冲突拦截”。

### 2.2 仍是静态配置的核心项

当前以下配置主要在服务启动时由 `config.json` 读取：

1. 角色定义：`roles.*`（密码、标签、`can_create_boards`、`can_manage_boards`）。
2. Agent 全局配置：`agent.enabled`、`agent.models`、`agent.tools.*`、`agent.max_board_context_chars`。
3. 服务基础配置：`service_name`、`supports_power_shutdown`、`max_import_bytes`。
4. 网络与证书配置：`listen_host`、`port`、`cert_file`、`key_file`。

### 2.3 用户反馈对应的两个缺口

1. 手机无法完整配置“PC 侧 AI 管理者策略”。
说明：板级字段已存在，但角色到模型的可用策略仍主要依赖 PC 静态 agent 配置，缺少统一远程入口。

2. 手机无法配置“PC 侧角色定义”。
说明：当前仅能在板级选择已有 `role_ids`，无法远程新增角色、改密码、改能力位，导致管理闭环不完整。

## 3. 设计逻辑

### 3.1 核心取舍

核心问题不是“把所有配置都做成热更新”，而是“在安全边界内把高频管理项动态化，低频系统项维持受控变更”。

取舍如下：

1. 高价值高频项动态化：角色、AI 策略、板级默认 AI。
2. 高风险低频项半动态化：服务名、关机能力、导入大小限制（支持在线改，必要时局部重建）。
3. 底层运行项保留重启：监听地址端口、证书路径。

### 3.2 新概念

1. Config Domain（配置域）
将配置按职责拆为 `auth`、`agent`、`board_policy`、`service_meta`、`runtime`。

2. Runtime Overlay（运行时覆盖层）
新增 `runtime_config.json`，覆盖 `config.json` 中允许动态化的字段。服务启动合并读取。

3. Config Revision（配置修订号）
每次远程修改产生单调递增 `revision`，用于并发保护与审计。

### 3.3 动态化范围矩阵

| 配置项 | 当前状态 | 目标状态 | 生效方式 |
| --- | --- | --- | --- |
| 角色定义（roles） | 静态 | 动态 | 立即生效 |
| 角色密码轮换 | 静态 | 动态 | 立即生效 |
| 角色能力位 | 静态 | 动态 | 立即生效 |
| Agent 模型列表 | 静态 | 动态 | 立即生效（重建内存配置） |
| Agent 工具开关 | 静态 | 动态 | 立即生效 |
| 板级 AI 管理者 | 半动态（板接口） | 动态 | 保持现有并增强 UI |
| 服务显示名 | 静态 | 动态 | 延迟生效（触发 mDNS 重注册） |
| `max_import_bytes` | 静态 | 动态 | 立即生效 |
| `supports_power_shutdown` | 静态 | 动态 | 立即生效 |
| `listen_host/port` | 静态 | 静态 | 需重启 |
| `cert_file/key_file` | 静态 | 静态 | 需重启 |

## 4. 核心数据结构

### 4.1 运行时配置总览

```json
{
  "schema_version": 1,
  "revision": 17,
  "updated_at": 1760000000000,
  "updated_by": "admin@192.168.3.74",
  "domains": {
    "auth": {
      "roles": {
        "admin": {
          "label": "管理员",
          "can_create_boards": true,
          "can_manage_boards": true,
          "password_set": true
        },
        "family": {
          "label": "家人",
          "can_create_boards": false,
          "can_manage_boards": false,
          "password_set": true
        }
      }
    },
    "agent": {
      "enabled": true,
      "models": ["qwen2.5", "gpt-oss:latest"],
      "tools": {
        "attachments": true,
        "web_fetch": false
      }
    },
    "service_meta": {
      "service_name": "LocalManager-klmm",
      "supports_power_shutdown": true,
      "max_import_bytes": 68719476736
    },
    "runtime": {
      "restart_required_fields": ["listen_host", "port", "cert_file", "key_file"]
    }
  }
}
```

说明：

1. `password_set` 仅用于展示，永不回传明文或可逆密文。
2. 角色密码写入采用单向摘要存储（见安全章节）。

### 4.2 角色 AI 可用策略

```json
{
  "role_agent_policy": {
    "admin": ["qwen2.5", "gpt-oss:latest"],
    "family": ["qwen2.5"],
    "guest": []
  }
}
```

用途：

1. 手机端配置板级 AI 管理者时，仅展示当前角色可选模型。
2. 服务端发言校验时，拒绝越权模型。

## 5. 接口定义（新增）

### 5.1 配置查询

1. `GET /system/config`
2. 权限：admin
3. 返回：当前运行时配置快照（脱敏）+ `revision`

### 5.2 配置更新（域级 Patch）

1. `PATCH /system/config`
2. 权限：admin
3. 请求头：`If-Match-Revision: <n>`（并发保护）
4. 请求体：

```json
{
  "auth": {
    "roles": {
      "family": {
        "label": "家人",
        "can_create_boards": false,
        "can_manage_boards": false,
        "password": "new-secret"
      }
    }
  },
  "agent": {
    "models": ["qwen2.5", "gpt-oss:latest"]
  }
}
```

5. 响应：新 `revision`、变更摘要、是否需要重启。

### 5.3 角色管理接口（可选拆分，便于手机 UI）

1. `GET /system/roles`
2. `POST /system/roles`
3. `PATCH /system/roles/{role_id}`
4. `DELETE /system/roles/{role_id}`（禁止删除 admin）

### 5.4 AI 策略接口

1. `GET /system/agent/policy`
2. `PATCH /system/agent/policy`

### 5.5 配置变更订阅接口（新增）

为解决“多台手机同时修改时缓存不一致”，增加轻量订阅机制（二选一，优先长轮询）：

1. `GET /system/config/changes?since=<revision>&timeout_ms=<n>`
2. 权限：admin
3. 行为：
  1. 若当前 `revision > since`，立即返回变更摘要。
  2. 否则阻塞到超时或有新变更（长轮询）。
4. 返回：
  1. `revision`
  2. `changed_domains`（如 `auth`、`agent`）
  3. `changed_paths`（如 `auth.roles.family`）
  4. `updated_at`
5. 客户端收到后按需拉取：`GET /system/config`（仅当本地草稿不冲突时自动刷新）。

### 5.6 板级接口增强

保持现有 `PATCH /boards/{id}`，增强约束：

1. 设置 `ai_manager_model` 时，必须属于当前操作者角色可用模型集合。
2. 若模型被全局禁用，返回 `invalid_ai_manager_model`。

## 6. 权限与安全设计

### 6.1 认证与授权

1. 仅 admin 可访问 `/system/config*`。
2. 非 admin 访问返回 `403 forbidden`。
3. 所有配置变更写审计日志（操作者、来源地址、变更前后摘要）。

### 6.2 密码处理

1. 角色密码仅支持“写入新值”，查询接口只返回 `password_set`。
2. 服务端存储由明文迁移为摘要（建议 `PBKDF2-HMAC-SHA256` 或等效方案）。
3. 支持“轮换生效窗口”：新旧密码可短时并存（可选，v2）。

### 6.3 并发保护与回滚

1. 采用 `revision` 乐观锁，防止多手机并发覆盖。
2. 每次变更前自动备份 `runtime_config.json.bak.<ts>`。
3. 提供 `POST /system/config/rollback?revision=<n>`（admin）。

### 6.4 多端并发一致性规则

1. 服务端以 `revision` 作为唯一真实时间线，所有写入必须携带 `If-Match-Revision`。
2. 若版本不匹配，返回 `409 revision_conflict`，响应体必须包含：
  1. `server_revision`
  2. `server_snapshot`（脱敏）
  3. `changed_paths`
3. 客户端不得盲目覆盖：
  1. 若本地无未提交草稿，直接切到最新快照。
  2. 若有草稿，进入冲突解决流程（见 7.4）。
4. 所有成功写入都广播到 `/system/config/changes`，确保其他手机在一个轮询周期内感知。

## 7. 手机端交互方案

### 7.1 入口规划

在家庭网络“进入设备后”的板列表页面新增“远程配置中心”入口（仅 `can_manage=true` 可见）。

### 7.2 页面结构

1. 角色管理
2. AI 策略管理
3. 服务元信息
4. 变更历史与回滚

### 7.3 板级配置联动

1. 打开板后“AI 管理者”弹窗改为调用新策略接口获取可选模型。
2. 支持手动输入模型名（高级模式），由服务端最终校验。

### 7.4 多手机并发编辑与防闪烁交互

为避免频繁刷新导致页面闪烁、输入中断、无法操作，手机端采用“草稿隔离 + 增量更新 + 节流渲染”三段策略。

1. 草稿隔离（Draft Isolation）
  1. 用户进入编辑页后，本地生成 `draft_base_revision`。
  2. 表单输入仅修改本地草稿，不直接覆盖屏幕上的服务端快照。
  3. 后台收到新 `revision` 时，若用户正在编辑，则只显示“有新配置可更新”横幅，不强制重绘表单。

2. 增量更新（Patch-first Refresh）
  1. 订阅接口返回 `changed_paths` 后，只更新受影响卡片。
  2. 未变化区域不重组 UI 状态，减少 Compose 触发重组范围。
  3. 列表项使用稳定 key，防止整表闪烁。

3. 节流渲染（Throttle + Coalesce）
  1. 变更事件在 300 到 500ms 窗口内合并一次渲染。
  2. 连续高频更新时，每 2 秒最多触发一次全页摘要刷新。
  3. 正在输入的字段禁止自动覆盖，除非用户主动点“应用最新”。

4. 冲突提交流程
  1. 提交时若返回 `409 revision_conflict`，弹出冲突面板：
    1. 显示“服务器已更新的字段”。
    2. 显示“本地未提交改动”。
  2. 提供三个动作：
    1. 重新基线并重放本地草稿。
    2. 放弃本地草稿并切到服务器版本。
    3. 仅提交不冲突字段。

5. 可操作性保护
  1. 保存按钮在网络抖动期间显示进度但不禁用返回与滚动。
  2. 任何后台刷新都不能关闭当前弹窗或重置滚动位置。
  3. 一次失败不清空草稿，允许离线后重试。

## 8. 实现路线

### Phase 1（高收益最小集）

1. 新增 `runtime_config.json` 与加载合并逻辑。
2. 新增 `/system/config`（读）与 `/system/roles`（增删改）。
3. 新增 `/system/config/changes` 长轮询接口。
4. 手机端新增“远程角色管理”页面与草稿隔离框架。
5. 角色变更即时生效，保留现有板接口。

### Phase 2（AI 策略闭环）

1. 新增 `/system/agent/policy`。
2. 板级 AI 管理者设置接入策略校验。
3. 手机端板内 AI 管理者改为“策略驱动列表 + 手动输入”。

### Phase 3（服务元信息动态化）

1. `service_name` 在线更新并触发 mDNS 重注册。
2. `supports_power_shutdown`、`max_import_bytes` 动态更新。
3. 引入配置变更审计与回滚 API。

## 9. 一致性校验

### 9.1 概念一致性

1. 角色定义属于 `auth` 域。
2. 模型可用策略属于 `agent` 域。
3. 板级 AI 管理者属于 `board_policy` 域（板元数据）。

三层分离后，职责边界清晰，避免“板级配置承担全局权限管理”。

### 9.2 状态完备性

需要覆盖以下状态：

1. 配置读成功。
2. 版本冲突（`revision_conflict`）。
3. 非法配置（模型不存在、角色重名、密码为空）。
4. 部分配置需要重启。
5. 编辑中收到远端更新（仅提示、不打断输入）。
6. 高频更新合并渲染（不闪烁）。

### 9.3 可测试性

建议新增测试集：

1. 角色增删改与认证链路回归。
2. 模型策略限制与板级 AI 管理者冲突校验。
3. 并发更新冲突与回滚。
4. 重启需求字段提示正确性。
5. 两台手机并发编辑下的草稿保留与冲突合并。
6. 高频变更推送下的 UI 稳定性（不丢焦点、不跳滚动）。

## 10. 收益与成本评估

### 10.1 预期收益

1. PC 无头部署可长期“手机优先运维”。
2. 角色与 AI 策略从静态文件迁移到可审计配置面。
3. 降低运维门槛，减少 SSH 手工改 JSON。

### 10.2 主要成本

1. 服务端新增配置域与持久化层。
2. 认证存储模型从明文迁移到摘要。
3. 手机端新增配置中心 UI 与交互状态管理。

### 10.3 风险

1. 配置热更新引入一致性问题（需 revision 与回滚兜底）。
2. 错误配置可能导致管理入口锁死（需保留本机 CLI 修复通道）。

## 11. 建议讨论点

1. 角色密码是否必须在 v1 就迁移到摘要存储。
2. 是否允许“非 admin 但 `can_manage_boards=true`”的中间管理角色配置系统项。
3. 手机端是否要提供“专家模式”（可编辑 JSON Patch）以减少前端开发量。
4. `/system/config/changes` 使用长轮询还是 SSE（考虑 Android 网络栈与后台保活限制）。
5. 冲突解决首版是否先做“字段级三方合并”，还是先做“整页重放草稿”。
