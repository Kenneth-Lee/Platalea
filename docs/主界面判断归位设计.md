# 主界面判断归位设计

## 1. 设计目的

`PlataleaApp.kt`（1095 行）经 AppShell 分层改造后，tab 接口已经收敛：主函数持一组 `MainTabFeature`，`MainTabContentHost` 按 tab 组合 content，换掉一个 tab 只需从 features 列表删一行。但其中的 `MainTabsRootContent` 局部函数（370 行）仍然混乱：名为"tab 内容宿主"，实际只有约 40 行属于 tab 切换，其余是 6 个功能对象的创建、8 组对话框的挂载调用、一个 13 分支的 `BackHandler`、退出函数中对 QUICK_NOTE 的点名特判、以及顶层 `activeRoute` 聚合中对 crypto/阅读器等具体域内部状态的逐一点名检查。

这些混乱共享同一个根源：**主界面收容了不属于它的判断**。主界面的本职是回答"现在屏幕显示什么 tab"，但现状它同时回答着"crypto 有没有确认框要弹"（挂载 CryptoDialogs）、"quickNote 退出时要不要确认"（requestExitApp 特判）、"阅读器的全屏查看器激活了没"（activeRoute 聚合）、"批量操作进行到第几项"（startBatchOperation 编排）。每多收容一个判断，下一个功能就多一个把胶水写进主界面的理由——G 系列六轮弹窗迁出只迁走了 UI 定义，挂载调用全部留在原地，就是这个循环的证据。

本设计以一条公理统摄重构：**同一个判断逻辑住在同一个模块**。据此重划主界面与各功能域的边界：主界面只保留对"屏幕被什么占据"的裁决（三个问题：门、全屏显示、当前 tab），其余判断一律归位到所属功能域；域需要越过主界面显示时，主界面只暴露抽象能力与机制（全屏显示、投影循环、退出协商），不实现也不点名任何具体功能。

定性：重构，全部既有行为等价。不改动各域内部结构、命令式协作模型（见《主界面AppShell分层设计》§2）、共享数据对象层与配置投影层。设计基线：2026-10 工作区（文件共享功能删除后）。

## 2. 设计逻辑

### 2.1 公理：判断与属地

程序的界面状态由一组**判断**构成——每个判断是运行中持续回答的一个有状态的问题："现在激活哪个 tab？""当前目录显示什么？""加密流程走到确认还是执行？""退出前有没有草稿要保存？"。每个判断有唯一的**属地**：持有其状态、并独占回答权的模块。模块的边界就是它收容的判断集合；一个模块读另一个模块的判断结果（调用方法、订阅状态）是正常的依赖，但把别人的判断状态或判断过程搬进自己，就是越界。

这条公理给出判定手段：对着一段代码问"这段在回答谁的问题"。`MainTabsRootContent` 里 13 分支的 `BackHandler` 回答的是十三个域各自的"我有没有东西要收回"；`requestExitApp` 里的 `QUICK_NOTE` 特判回答的是速记域的"退出前要不要保存"；`activeRoute` 聚合里逐个检查 `archiveReader.routeActive`、`crypto.passEdit`，回答的是各域的"我的查看器激活了吗"。答案都不是"主界面"——它们放错了地方。后续各节逐类给出归位办法。

### 2.2 主界面只回答三个问题

主界面是屏幕布局互斥事实的裁决者：任一时刻屏幕被一个东西占据。这个"占据"只有三种形态，构成主界面全部的判断：

| 判断 | 回答的问题 | 取值 |
| --- | --- | --- |
| 程序级门 | tab 系统可用吗 | 未解锁 / 无根目录 / 通过 |
| 当前全屏显示体 | 有东西盖住 tab 界面吗 | 空 / 一个功能的显示 |
| 当前 tab | tab 界面显示哪个域 | 14 个 tab 之一 |

门与全屏显示的区别：门是 tab 系统**尚未可用**的前置态（此时任何域投影都不该存在），全屏显示是 tab 系统可用但被功能**临时占据**（阅读器、批量执行页、密码编辑器）。现状顶层 `when` 已按这四分支渲染（unlock / 无根 / activeRoute / MainTabsRootContent），概念上正是对这三问的回答——本设计将其定型为显式的屏幕分派结构，主界面的渲染代码收敛为按三个答案分派，不再出现任何域的名字。

### 2.3 投影：域的显示不需要主界面协调

对话框挂载是现状最大的乱源。归位的推理从 Compose 的一个机制事实出发：`Dialog` 是独立的模态窗口，不参与布局仲裁——它弹在谁的组合里都是全屏居中，**根本不存在"必须由主界面协调显示位置"的需求**。"crypto 有没有确认框要显示"是 crypto 域的判断，判断的属地就有显示的属地：crypto 域在**自己的投影**里组合 `CryptoDialogs`，对话框的状态、返回键处理、完成回调全部内聚，主界面不出现这行调用。

投影分两种，区别在组合锚点的生命周期：

- **content 投影**：tab 激活时组合（现 `MainTabFeature.content`，组合即进入、离开即离开，不变）；
- **常驻投影**：不依赖 tab 激活、只要域活着就可能要显示的对话框级投影（现 `MainTabFeature.overlay` 属性的推广）。

常驻投影解决一个真实场景：browser 域发起加密请求后用户切到播放器 tab，加密确认框必须仍然在场。它不能住在 browser 的 content 里（已离开组合），也不能住主界面（判断不属地）——所以每个域声明一个 overlay，主界面**循环组合所有域的 overlay**。循环是机制不是知识：主界面不知道也不需要知道某个 overlay 里面有没有对话框、是什么对话框；域未活动时其 overlay 组合出空。速记密码框、播放目标对话框已用此模式（现状 4 处 `override val overlay`），本设计把它定为所有对话框的统一归宿。

由此，`MainTabsRootContent` 里的 8 组对话框挂载全部迁走：CryptoDialogs/ArchiveOperationDialogs/QuickObfuscateDialogs 归各自工作流域的 overlay；RootSwitchDialog/ChangeRootConfirmDialog/OverwriteSaveConfirmDialog 归 browser 域外挂工作流（rootSwitch/browserSave 本就是 browser 域对象）的 overlay；BulletinForwardTargetFlow 归家庭网络域（`bulletinForwardPayload` 状态随之从主界面迁走，browser 的出口回调从"存 payload 到主界面"改为直呼 family 域 API）。

### 2.4 全屏显示体：记录归主界面，内容归域

盖住 tab 栏的显示（阅读器全屏、批量执行页、密码编辑器）参与布局互斥，必须由主界面统一记录"当前谁占据着屏幕"——但"占据的内容是什么"是发起域的判断。现状的 `activeRoute` 聚合违背属地原则：

```kotlin
val activeRoute = transientRoute
    ?: operationRun?.let { ... }
    ?: if (archiveReader.routeActive) ...   // 阅读器域的判断搬进主界面
    ?: if (epubReader.routeActive) ...
    ?: crypto.passEdit?.let { ... }
```

它逐个检查各域内部状态，每新增一种全屏功能就要在主界面加一个分支。归位后主界面只记录一个"当前全屏显示体"（现 `transientRoute` 已是正确形态：一个可写的记录位），各域在进入全屏态时设置、退出时清除——即用户提出的"全屏显示体"接口：主界面暴露"全屏显示"这个能力，让功能无条件设置，不关心设置的是什么。冲突裁决规则只有一条：后设置者覆盖（与现状聚合的优先序语义一致——最新交互优先），由这个记录位自身的写语义承载，主界面无需比较各域状态。

### 2.5 退出协商与返回键

退出是程序级行为（finish activity），执行权归主界面；但"退出前要做的事"可能是域的判断——速记域退出前要保存/确认草稿。现状 `requestExitApp` 点名 `QUICK_NOTE`，正是判断搬运。归位为**退出协商**：主界面收到退出意图时，把意图交给当前激活的 tab 功能，由它决定拦截（域内自己弹确认、处理完再放行）或放行；放行后主界面执行自己的公共策略（快捷方式直达跳过确认、否则双击退出）。主界面全程不知道"谁会拦截、为什么拦截"。

返回键是退出协商的入口之一，也是 13 分支 BackHandler 解体的钥匙。Compose 的 `BackHandler` 由组合树中后组合者优先——**谁挂载的 UI 谁就能挂它的返回键**：对话框在域 overlay 里，返回键就在同一个 overlay 里；browser 的待处理面板在 content 里，返回键就在 content 里；全屏体的返回键在其 RouteHost 里（现状已如此）。归位后主界面的 `BackHandler` 只剩一件事：把退出意图送入协商。

### 2.6 执行能力：进度与批量执行页

`runWithProgress` 与 `startBatchOperation` 是现状的两个局部函数，被十几个域捕获——它们是"重力井"的主要来源。按属地拆解：

- 进度状态（"操作进行到哪"）的属地是**发起操作的域**。进度框 UI（`OperationProgressDialog`）是无判断的共享 UI 件，谁的状态谁组合。
- 批量执行页（逐项执行、展示结果）有自己的完整判断（执行到第几项、是否完成），是一个**无 tab 的功能域**，以全屏显示体形态出现（现 `operationRun` 已是，保持）。

由此二者从主界面消失，收敛为一个共享服务对象 `OperationRunner`：组合根创建、注入需要它的域，内部持进度状态与批量执行页状态，`overlay` 提供进度框投影，执行页经全屏显示出现。各域调用 `runner.run(label) { ... }`，等价于现状 `runWithProgress`，但主界面不再定义也不持有它。

### 2.7 域出口拆窄与组合根

`BrowserTabHostDependencies` 的 22 个字段把"browser 发起一切域"捆成一包，本质是把接线当成了一个概念。按属地拆窄：每个目标域向 browser 暴露自己的窄 API（阅读域的 `ReadingLauncher` 已是此形态的样板；crypto 一个 `open(request)`；family 一个 `forward(payload)`；播放器域已有 `PlayerTabApi`）。**接线在组合根**：组合根创建全部域对象、把各域 API 交给需要它的域——创建关系是"谁持有谁"的事实陈述，不是判断搬运，留在组合根正当。`MainTabsRootContent` 同时拆为参数化的顶层 composable，消灭 20+ 变量的闭包捕获；组合根本身收敛为"创建 + 接线 + 对三问的分派"，即《主界面AppShell分层设计》Step 4 预言的 200-300 行终态。

### 概念空间

以上推理引入的概念汇总：

* **判断**：运行中持续回答的一个有状态的问题；**属地**：唯一持有并回答它的模块。模块边界 = 判断集合（§2.1 公理）。
* **主界面三问**（程序级门 / 当前全屏显示体 / 当前 tab）：主界面收容的全部判断，回答"屏幕被什么占据"（§2.2）。
* **投影**：域判断在组合树的显示，分 content 投影（组合即进入）与常驻投影（overlay，不依赖 tab 激活）。主界面循环组合 overlay 是机制，不是知识（§2.3）。
* **全屏显示体**：盖住 tab 界面的功能显示；主界面只记录当前是谁（后设覆盖），内容渲染完全在域内（§2.4）。
* **退出协商**：退出意图经激活 tab 拦截或放行，公共退出策略（双击确认等）归主界面（§2.5）。
* **共享 UI 件**：无判断的纯显示组件（进度框、密码框），归调用方组合（§2.6）。
* **OperationRunner**：跨域共享的执行编排服务对象，进度状态属地，投影经 overlay 与全屏显示体（§2.6）。
* **组合根**：创建全部对象并接线的顶层作用域；接线陈述持有关系，不搬判断（§2.7）。

## 3. 核心数据结构

本设计是重构，域内部数据结构不变；变化集中在三处结构面。

**主界面的状态**（组合根持有，即对三问的回答）：

```kotlin
var gate by remember { mutableStateOf<Gate>(...) }           // 程序级门（解锁/无根/通过）
val fullscreen = rememberFullscreenDisplay()                 // 当前全屏显示体（可设可清）
var activeTab by remember { mutableStateOf<MainTab?>(null) } // 当前 tab（现 currentMainTab）
```

**功能域呈现接口**（`MainTabFeature` 扩展，overlay 语义升格为常驻投影并加退出协商）：

```kotlin
internal interface MainTabFeature {
    val tab: MainTab
    val content: @Composable () -> Unit          // content 投影（不变）
    val overlay: (@Composable () -> Unit)? get() = null  // 常驻投影（语义升格）
    /** 退出协商：收到退出意图，域拦截返回 true（自行处理），放行返回 false */
    fun onExitRequest(): Boolean = false
}
```

**无 tab 功能域**（crypto 工作流、OperationRunner 等）：同构的窄接口——`val overlay: (@Composable () -> Unit)?`（常驻投影）+ 域自己的 API（如 `crypto.open(request)`）；需要全屏时经全屏显示接口设置/清除。

**OperationRunner**（共享执行服务）：

```kotlin
class OperationRunner(scope) {
    val progress: State<OperationProgress?>        // 进度状态（判断属地）
    val overlay: @Composable () -> Unit            // 进度框投影
    fun run(label: String, block: suspend ...)     // 等价现 runWithProgress
    fun runBatch(label, names, block)              // 等价现 startBatchOperation（经全屏显示体）
}
```

三者的协作总结：组合根创建域与 runner、接线、把 overlay 们收进一个循环列表；主界面 composable 按三问的答案分派（门未过显示门界面；有全屏显示体则显示它；否则显示 tab 界面），并在最外层组合全部 overlay。

## 4. 接口定义

**主界面暴露给域的能力**（仅两类，均为抽象机制）：

```kotlin
// 全屏显示接口：功能进入全屏态时设置、退出时清除，主界面不关心内容
interface FullscreenDisplay {
    fun set(route: TransientRoute)   // 后设置者覆盖
    fun clear(route: TransientRoute) // 仅当当前仍是该 route 时清除，防误清后来者
}

// 退出执行：域协商放行后（或无需协商时）调用的最终动作
fun exitApp()
```

**域间出口**（以 browser 域为例，22 字段包替换为一组窄 API）：

```kotlin
// browser 域构造参数（组合根接线）
browserTabFeature(
    state = browserTab,
    reading = readingLauncher,      // 阅读域：ReadingLauncher（已有）
    crypto = cryptoApi,             // 加密域：open(request) + 域内自显流程对话框
    family = familyForwardApi,      // 家庭网络域：forward(payload)，对话框域内自显
    player = playerTabApi,          // 播放域（已有）
    navigator = mainTabNavigator,   // 主界面：requestOpenMainTab（切 tab 的唯一出口）
    runner = operationRunner,       // 执行服务：run/runBatch
    ...
)
```

判定规则（承接《主界面AppShell分层设计》§4.1，替换成本检验不变）：一个 UI 元素或状态的归属，依次问——它回答"屏幕被什么占据"吗（归主界面三问）；它回答某功能域的流程或内容吗（归该域 content/overlay）；它无判断纯显示吗（共享 UI 件，调用方组合）；它是多域共用的执行编排吗（归 OperationRunner）；它是被多方读写的底层数据吗（归共享数据对象）。五问下来没有归属的，不建新家，回到引入它的域重新审视。

## 5. 迁移路径

每批行为等价、独立编译提交：

1. **B1 对话框归域**：8 组挂载从 `MainTabsRootContent` 迁入各域 overlay（crypto/archiveOps/quickObfuscate/rootSwitch/browserSave/family 六域）；`progressOp`/进度框随 `OperationRunner` 服务建立归位；主界面删 13 分支 BackHandler，逐分支下沉到对应 overlay/content（Compose 后组合者优先，真机验证返回键次序不变）。
2. **B2 退出协商**：`requestExitApp` 去 QUICK_NOTE 特判，`MainTabFeature.onExitRequest` 上线；速记域实现拦截，双击退出与快捷方式 bypass 留主界面公共策略。
3. **B3 全屏显示统一**：`activeRoute` 聚合删除，全屏显示接口上线；archiveReader/epubReader/crypto 在进入/退出全屏态时自行设置/清除（域内一处 LaunchedEffect 或状态变更点）。
4. **B4 出口拆窄**：`BrowserTabHostDependencies` 按目标域拆成窄 API 注入；`bulletinForwardPayload` 等主界面中转状态随迁 family 域。
5. **B5 主界面定型**：`MainTabsRootContent` 拆参数化顶层 composable；组合根收敛为"创建+接线+对三问的分派"，目标 200-300 行。

## 6. 否决的备选

**对话框统一走全屏显示**（对话框即轻量的全屏显示体，主界面只记录一种占据）：被否。对话框与全屏显示体的本质差异是是否参与布局互斥——对话框不盖 tab 栏、不阻止其他对话框，把两类塞进同一条占据记录会人为制造互斥并丢掉 Compose Dialog 的免费模态语义。

**overlay 用注册/订阅总线**（域动态注册 overlay 回调列表，主界面订阅）：被否。域对象在组合根一次成型，overlay 是域的固有投影面，声明为接口属性即可；总线引入生命周期对齐与顺序问题，在单活动前提下（《主界面AppShell分层设计》§2.1）无正确性收益。

**维持 G 系列模式继续逐个剜**（每批迁一个对话框 UI，挂载留主界面）：被否。这正是走到现状的路径——挂载调用与闭包参数的存量只增不减，判断搬运没有被原则性阻止。
